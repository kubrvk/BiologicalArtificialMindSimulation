# BioMind — UE5.7 C++ Port — Project Status Handoff

## What this project is

BioMind is a mental-health simulation game: an LLM-driven character whose behavior is grounded in a real-time biological simulation (hormones, brain regions, neurotransmitters, emotions, vitals, mental-health indices) rather than free-form roleplay. The LLM never controls the simulation — it only narrates/converses based on it.

This is a from-scratch C++ port of a working HTML/JS prototype into Unreal Engine 5.7. The original prototype lives at `Saved/HTML/` in this project (reference only, not part of the UE build): `bio_state.js`, `engine.js`, `bio_constants.js`, `systems/{character,development,idle_loop,llm,therapy}.js`, `pharmacology.js`, `memory.js`, plus a Turkish README (`llm-server/README.md`) specifying the local-LLM integration approach that was followed exactly.

## Delivery approach (important context for how work has been done)

- No interactive Unreal Editor GUI access — everything has been built by writing/editing C++ source files directly and compiling via command line (`Engine\Build\BatchFiles\Build.bat`).
- Verification has been done **headlessly** via `UnrealEditor-Cmd.exe -game -nullrhi -unattended -ExecCmds="..."`, using custom console commands (see reference list below) and grepping resulting logs, since there's no way to click through the editor.
- Delivered phase-by-phase, each phase compiled and headlessly verified (often with exact hand-calculated math checks against the ported JS formulas) before moving to the next.
- Work has been fully faithful to the original JS logic/formulas wherever possible; any deliberate deviation or simplification is commented in the code and listed below.

### Hard-won process lessons (apply these in the new chat)
- **Never trust the bash tool's reported exit code when the build command is piped through `tail`/`grep`** — that reflects the pipe's exit code, not `Build.bat`'s. Always explicitly `grep -n "Result: Succeeded\|error C"` in the actual log file content.
- Git Bash mangles absolute paths starting with `/` (e.g. `/Engine/Maps/Entry` becomes a mangled Windows path). Use `MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL="*"` before such commands.
- Always include `quit` in `-ExecCmds`, or use the custom `idle.RunFor <seconds>` command (schedules a graceful self-quit after N real seconds) for timed/async tests. Killing the process externally (`timeout`, `taskkill`) can lose buffered stdout that was never flushed to the log file, and leaves stray `UnrealEditor-Cmd.exe`/`llama-server.exe` processes holding DLLs locked, which breaks the next build (`LINK : fatal error LNK1104: cannot open file ...dll`). Check `tasklist //FI "IMAGENAME eq UnrealEditor*"` and `taskkill //F //PID <pid>` before rebuilding if a previous headless run might still be alive.
- **`-ExecCmds` splits on commas, not semicolons** (confirmed against UE 5.7's `ParseExecCommands.cpp`) — semicolons all get swallowed into the first command's argument string instead of starting new commands.
- **Headless Python editor scripting works without any GUI**: `UnrealEditor-Cmd.exe <uproject> -run=pythonscript -script="<absolute path>.py" -EnablePython -unattended -nullrhi -nosplash`. `PythonScriptPlugin` is **not** enabled by default in this project's `.uproject` (`EnabledByDefault: false` in the plugin itself) — `-EnablePython` force-enables it for that one run without needing to edit the `.uproject`. The `-script=` path must be absolute (relative paths resolve against `Engine/Binaries/Win64`, not the project root).
- **`UDataTable` CSV import for `TMap<FName,float>` fields** does *not* use `(Key=Value,Key=Value)` — that silently imports as an empty map with no error surfaced. The real `FMapProperty::ImportText` format is `((Key,Value),(Key,Value))` (confirmed by reading `PropertyMap.cpp`). Always spot-check imported rows (e.g. `unreal.DataTableFunctionLibrary.export_data_table_to_json_string(dt)` in a throwaway verification script) rather than trusting a "success" return from the importer.
- **llama-server only serves one completion request at a time.** The user-reported "sometimes works, sometimes errors" chat bug turned out to be exactly this: the idle loop's background thought/dream generation firing while another request (a player chat message, or another idle-loop request) was still in flight caused the *second* request to fail, and previously that failure was misreported as a generic "server unreachable" error with no indication of the real cause. Confirmed by headless testing: with no request-overlap guard, every request after the first two failed for the rest of the session; with the guard (`UBioLLMSubsystem::bChatRequestInFlight`, see below) failures become rare, clearly-labeled "LLM is busy" messages instead of a cascade of "unreachable" errors.
- **Never append `,quit` after `idle.RunFor N` in the same `-ExecCmds` string.** `idle.RunFor` already schedules its own graceful self-quit after N seconds; a `quit` chained right after it in the same comma-split list fires *immediately* instead of waiting, so the run exits after ~1 second instead of actually testing anything. This silently invalidated several "verified clean, zero errors" headless runs in the Enhanced AI Movement work below before being caught — always use `idle.RunFor N` alone and let it self-quit.
- **This project is now a git repository** (it wasn't for most of its history — see `.gitignore`, which excludes `Binaries/`, `Intermediate/`, `Saved/`, and the 2.3GB LLM `.gguf` model). Commit after meaningful working checkpoints, especially before any Blueprint/asset-editor work that can't be diffed/undone the way C++ can.

## Module structure

- **`BioMindCore`** — the simulation itself: state struct, data tables, tick pipeline, character/save, development, therapy classification logic. No UI/LLM dependency.
- **`BioMindLLM`** — local LLM process management, HTTP client, autonomous idle-loop subsystem. Depends on `BioMindCore`.
- **`BioMindUI`** — the dashboard widget (pure native Slate, no `.uasset` widget blueprint). Depends on `BioMindCore` + `BioMindLLM`.
- **`BioMind`** — thin glue module: GameMode, PlayerController, and the 3D character actor/player pawn base classes. Depends on all three above (including a direct `BioMindLLM` dependency now, added so `BioMindPlayerController.cpp` can call `EnsureServerStarted()` without relying on `BioMindUI`'s transitive include path).

Also `FBioEpisodicMemory`, `EBioCircadianPhase`, `EBioIdleState`, `EBioBiologicalSex`.
- **`BioKeys.h/.cpp`** — `FName` constants for every hormone/brain region/neuro system/emotion/MH index/preset/development phase/memory category/therapy intervention/stimulus type, plus `AllX()` array accessors.
- **`BioDataTables.h/.cpp`** — row structs (`FBioHormoneDefRow`, `FBioDrugDefRow`, `FBioPresetRow`, `FBioDatingProfileRow`, `FBioDevelopmentPhaseRow`, `FBioTherapyInterventionDefRow`, `FBioStimulusDefRow`, etc.) + `BioDefaultData::GetX()` accessors. **`GetDrugDB()`/`GetPresets()`/`GetDatingProfiles()` now load from real `UDataTable` assets** (`Content/Data/DT_Drugs.uasset`, `DT_Presets.uasset`, `DT_DatingProfiles.uasset` — user can open/edit these directly in the Unreal Editor, including assigning `MedicationImage`/`Portrait` `TSoftObjectPtr<UTexture2D>` fields) via a `TryLoadDataTableRows<T>()` helper, **falling back to the original hardcoded C++ data (logged warning) if the asset can't be loaded** — a renamed/deleted asset degrades gracefully instead of breaking the game. The remaining tables (hormone/brain-region/neurotransmitter/emotion/MH/thought-template/development-phase/memory-category/therapy/stimulus) are still C++-only for now — same migration pattern, just not done yet, since they weren't the tables the user actually asked to edit. Assets were authored via `Content/Python/import_bio_datatables.py` (headless, one-time — see below).
- **`BioSimEngine.h/.cpp`** — `FBioSimEngine::Step()`: the 11-stage tick pipeline (Clock → HPA → Peripheral axes → Neurotransmitters → Pharmacology → Therapy → Brain regions → Emotions → Vitals → Mental health → Memory/sleep → Thought/idle-state). Faithful port of `engine.js`, including its sequential read-after-write formula ordering.
- **`BioSimTuning.h/.cpp`** — `UBioSimTuning : UDeveloperSettings`, editable lerp-rate constants.
- **`BioCharacterSim.h/.cpp`** — `UBioCharacterSim : UObject`. One instance = one character: `CharacterId`, `CharacterName`, `State` (FBioState), `AgeYears`, `BiologicalSex`, `bDevelopmentComplete`, `EpisodicMemories`. `ApplyPreset()`/`ResetToDefault()`.
- **`BioCharacterJson.h/.cpp`** — save/load as **one human-readable JSON file per character** (user's explicit request, not `USaveGame`), via `FJsonObjectConverter` (auto-serializes the whole `FBioState` struct). Files saved at `Saved/BioMindCharacters/<SanitizedCharacterName>.json` — filename is the character's name (sanitized for filesystem), not a GUID. **Known collision risk**: two characters sharing a name overwrite the same file (last save wins) — accepted tradeoff for human-readable filenames.
- **`BioDevelopmentSystem.h/.cpp`** — `FBioDevelopmentSystem`: `GetPhase(Age)` (4 life stages: infancy 0-2, childhood 2-12, adolescence 12-18, young adult 18-25), `ApplyPhaseHormones` (lerps toward phase defaults + sex-specific puberty overrides), `ApplyMemoryEffect` (category-based hormone deltas + amygdala/PTSD/hippocampus tagging).
- **`BioTherapySystem.h/.cpp`** — `FBioTherapySystem`: `ClassifyTherapyType` (regex keyword classifier, 7 intervention types), `ApplyImmediate`, `RegisterSustained` (ramp mechanic: new registrations compute ramp from session/onset, but re-triggering an active effect just nudges ramp +0.1 rather than recomputing — an original-source quirk, replicated faithfully).
- **`BioMindCharacterSubsystem.h/.cpp`** — `UBioMindCharacterSubsystem : UGameInstanceSubsystem`. Central owner of the active character + main tick loop + growth loop. Delegates: `OnBioStateUpdated`, `OnGrowthProgress`. Key methods: `StepOnce`, `NotifyStateChanged` (Phase 20 -- re-broadcasts `OnBioStateUpdated` with the current state without running the sim engine, for UI-only refreshes like activity progress), `SetRunning`, `SetTickIntervalSeconds` (clamped to `[0.05, 600]` seconds), `ApplyPreset`, `CreateNewCharacter`, `SaveActiveCharacter`, `LoadCharacter`, `DeleteCharacter`, `ListSavedCharacterIds`, `BeginAcceleratedGrowth`, `StopAcceleratedGrowth`, `RewindToAge`, `InjectMemoryAt`, `AdministerDrug`, `ProcessTherapyMessage`, `InjectStimulus`, `DumpStateToLog`. **`StepOnce()`/`NotifyStateChanged()` both funnel through a private `BroadcastStateUpdated()`** (Phase 21) guarded by `bIsBroadcastingState` -- fixes a real `EXCEPTION_STACK_OVERFLOW` crash where a listener (`ABioCharacterAIController::FinishActivity`) triggered a nested `NotifyStateChanged()` from inside its own `OnBioStateUpdated` handler, and since the delegate is a synchronous multicast, the nested broadcast re-entered the same handler while its state was still mid-transition, matching the same "should finish" condition again and recursing forever. A nested broadcast attempt while one is already in progress is now silently swallowed (listeners already see the latest state by reference either way) rather than processed. **Both `Initialize()` (the auto-created "Default" character) and `CreateNewCharacter()` call `StepOnce()` immediately after `ApplyPreset()`** — `Emotions`/`Vitals`/`CurrentThought` are derived-only-in-`Step()` values, so without this a fresh character shows all-zero emotions/empty thought until the next scheduled tick (a real bug found and fixed once `RealSecondsPerTick` became slow enough to make the gap visible — see completed phase 15).
  - **Important architectural limitation**: tracks **one active character at a time**. No simultaneous multi-character roster ticking yet.

### BioMindLLM
- **`BioLLMTypes.h`** — `EBioLLMStatus` (Idle/Loading/Connected/Error), `FBioLLMChatMessage`, `FBioLLMCompletionDelegate`.
- **`BioLLMSubsystem.h/.cpp`** — `UBioLLMSubsystem : UGameInstanceSubsystem`. Launches `llama-server.exe` as a hidden child process (`EnsureServerStarted`/`StopServer`, lazy — only on first use) with `-ngl 999 -t <NumCores>` (GPU offload if the binary supports it, explicit thread count — safe to always pass even on a CPU-only build), polls `/v1/models` for readiness, HTTP chat via `FHttpModule` (OpenAI-compatible `/chat/completions`, preserves `chat_template_kwargs: {enable_thinking: false}` to disable Qwen3's hidden reasoning, `SetTimeout(180.f)` since CPU-only inference can legitimately take a while). Four generation modes: `GenerateSpeech` (400 tok/0.82), `GenerateThought` (80 tok/0.92), `GenerateDream` (120 tok/1.0), `GenerateTherapyResponse` (350 tok/0.85). Builds bio-grounded system prompts from live `FBioState`, templated via `UBioLLMPromptSettings` (below). **`bChatRequestInFlight` guard** — llama-server only serves one completion request at a time; this was the real root cause of "sometimes works, sometimes errors" (the idle loop's background thought/dream generation colliding with a player chat message, or with each other, previously surfaced as a confusing generic "server unreachable"). Now a second request while one's in flight fails fast with a clear "LLM is busy" message instead of corrupting/timing out the shared connection.
- **`BioLLMPromptSettings.h/.cpp`** *(new)* — `UBioLLMPromptSettings : UDeveloperSettings` (same pattern as `BioSimTuning`, shows up in Project Settings → "BioMind LLM Prompts", no C++ rebuild needed to tweak). Editable `SystemPromptTemplate` (`{Name}`/`{StateSummary}` tokens), `ArrivalGreetingPrompt`, `DepartureFarewellPrompt` (defined, not yet wired to a call site).
- **`BioIdleLoopSubsystem.h/.cpp`** — `UBioIdleLoopSubsystem : UGameInstanceSubsystem`. Autonomous idle behavior, on two independent clocks: **Dreams** are still tick-based (`HandleBioStateUpdated`, watches `OnBioStateUpdated`, fires during `DeepSleep` phase every 48 ticks — `DreamIntervalTicks`, tied to the circadian phase so it has to be tick-based). **Thoughts** are no longer tick-based at all — `HandleThoughtTimerTick()` runs on its own real-world `FTSTicker` (`UBioSimTuning::ThoughtRealSecondsInterval`, default 120s), independent of however fast/slow `RealSecondsPerTick` is configured, so autonomous thoughts keep a human-normal cadence regardless of the biology clock's speed. Both fall back to template lines if the LLM isn't connected. **Contains a fixed real bug worth knowing about**: `Initialize()` must call `Collection.InitializeDependency<UBioMindCharacterSubsystem>()` / `<UBioLLMSubsystem>()` before `GetSubsystem<T>()` — plain `GetSubsystem<T>()` does not force-create cross-module dependencies, so without this the idle loop silently never fired (found via careful diagnostic logging, not assumption). Thought and dream generation can still occasionally collide with each other (independent clocks firing close together) — surfaces as an occasional "LLM is busy" log line, harmless/expected, not the same bug as above.
- LLM binaries live in a project-root `LLM/` folder (outside `Content/`, so never cooked as an asset): `LLM/llm-server/bin/llama-server.exe` (+ DLLs), `LLM/llm/Qwen3-4B-Q4_K_M.gguf` (2.3GB model). Server listens on `http://127.0.0.1:8080/v1`.

    - **Real bugs found and fixed in `ABioCharacterAIController` during this work** (several exposed by the plugin swap and the new montage-section logic below, not pre-existing):
      - **Arrival didn't snap position, only rotation.** `OnMoveCompleted`'s success branch always snapped yaw to the interactable's facing but never corrected location — `MoveToLocation`'s `AcceptanceRadius`/`ReachRadiusOnSpline` tolerance only guarantees arrival *near* the target, not exactly on it, which looked fine for casual walking but left the character visibly offset from furniture once precise seated poses mattered. Now snaps both location and yaw to `CharacterSnapPoint` (see below) on arrival.
      - **A three-point system replaces the old single `InteractionPoint` for furniture interaction, after several iterations of misassigning which point does what:** `InteractionZone` (existing `UBoxComponent`) is the **pathing target** `MoveToLocation` walks to (repositionable independently of the other two, e.g. out in front of a chair); `CharacterSnapPoint` (new `UArrowComponent`) is the **exact transform the character snaps to on arrival** (nudge this by eye to compensate for skeletal-mesh-origin differences between `BP_BioCharacter`'s mesh and whatever preview mesh is assigned); `PreviewMeshComponent` (the debug pose-preview aid, below) is now attached to `CharacterSnapPoint` (not `InteractionPoint`) so the editor preview and the real character's eventual snap position are always the same transform, never two independently-drifting points. Also disabled `InteractionZone`'s collision entirely (`NoCollision`, `GenerateOverlapEvents = false`) — confirmed nothing in the codebase binds to its overlap events at all (it's a pure visual/gizmo aid), but its collision was unintentionally visible to Enhanced AI Movement's real-time avoidance sensors, making the AI swerve around it like an obstacle instead of walking into it.
      - **Sitting-preemption left the old activity's montage playing forever.** `EvaluatePriority()`'s Sitting-preemption path (Phase 18 — a higher-priority need can interrupt a sit mid-activity) calls `GoToInteractable()` directly and never went through `FinishActivity()`, so it never stopped the currently-playing montage — the character would visibly stay in the old sit pose while walking off to a logically-unrelated task and completing it normally. Fixed by having `GoToInteractable()` unconditionally call `StopActionMontage()` (an immediate stop, not a graceful wait — preemption means something urgent came up) whenever it starts a new task.
      - **`FinishActivity()` now waits for a real "stand up" transition before moving to the next task, with a safety-net timeout.** Previously `FinishActivity()` cleared state and called `EvaluatePriority()` (which can immediately start walking to the next objective) in the same frame it told the montage to blend out — the AI would start walking to the next furniture piece while still visibly sitting/lying down mid-blend. Now, if the currently-playing montage has a section literally named `"End"`, `FinishActivity()` jumps to it and defers state-clearing/the next `MoveToLocation` until it actually finishes (via `Montage_SetEndDelegate` → `OnStandUpMontageEnded` → `FinishActivityContinued()`), falling back to the previous immediate behavior for any activity with no montage or no `"End"` section. **Guarded with a 5-second timeout (`OnStandUpTimeout`)**: if a montage's `"End"` section is misconfigured (its own "Next Section" still looping back into itself instead of `"None"` — confirmed this is exactly what happened with several of the user's own authored montages, all built by stretching one single loop clip across the whole Start/Loop/End timeline rather than using distinct clips per section) the end delegate never fires, and without the timeout the character would be stuck forever mid-task with a frozen HUD progress line. The timeout self-recovers every time regardless of the montage authoring mistake.
      - **A second, related bug the montage-wait exposed: `HandleBioStateUpdated` re-triggered `FinishActivity()` on every broadcast while a stand-up wait was already pending**, since `CurrentActivity` deliberately stays set to the finishing activity throughout that wait (that's the whole point). Without a guard, every tick during the (up to 5-second) wait re-entered `FinishActivity()`, redundantly re-logging "finished X" and re-jumping the montage each time. Fixed with a `bFinishActivityInProgress` flag, set when the wait begins and cleared in `FinishActivityContinued()` (the single point both the delegate and the timeout path converge on) — also defensively cleared in `GoToInteractable()`/`OnUnPossess()`.
    - **New debug/authoring aid on `ABioInteractableActor`**: `PreviewMeshComponent` (a `USkeletalMeshComponent`, hidden and non-ticking at runtime via `BeginPlay`) plus `PreviewSkeletalMesh`/`PreviewPoseAnimation` properties — assign the same mesh `BP_BioCharacter` uses and a sit/sleep `AnimSequence` to see, live in the level viewport via `OnConstruction`, exactly what pose/angle the character will end up at, with no Play needed. Deliberately **freezes on the animation's last frame** rather than looping it (`SetPosition(GetPlayLength(), false)` + `SetPlayRate(0.f)`) — most sit/sleep clips are a stand-to-seated *transition*, not a self-contained loop, so looping the whole clip just replays the stand-up motion over and over, which looked like "snapping back to standing" every cycle. Purely an authoring aid, decoupled from the real runtime montage system (`DT_WorldActions`) on purpose, since one interactable type (e.g. Kitchen) can map to multiple activities with different poses.
    - **`DT_WorldActions` now has real montages assigned to 6 of 7 rows** (`Sleeping`→`Anim_KA_2_bed`, `Sitting`→`Anim_KA_Sit_CrossLegs_Loop_Montage`, `Eating`→`Anim_KA_5_table`, `UsingBathroom`→`Anim_KA_6_bathroom`, `GettingDrink`→`Anim_KA_4_kitchen`, `Showering`→`Anim_KA_3_shower`; only `PreparingFood` still unset) — **known issue, not yet fixed**: per the `OnStandUpTimeout` warnings firing for all of them in testing, all six montages likely share the same authoring mistake as the original Couch one (Start/Loop/End are time-slices of one single stretched clip rather than distinct clips, so "End" never reaches a real terminating point) — each needs a genuine distinct stand-up clip in its "End" section with that section's own "Next Section" set to `"None"`, not looping.
    - Verified throughout via proper (not `,quit`-truncated, see the process-lessons note above) headless runs: `player.InviteHome noah,bio.Speed 4,idle.RunFor 90-120` sequences showing full Couch→Drink→Sleep→Bathroom→Kitchen cycles with zero crashes/ensures/asserts at every step of this work. **Not yet visually confirmed** (headless/nullrhi can't show this): whether the walking pace/turning actually looks natural in a real play session, whether `CharacterSnapPoint` now lines up the character with furniture correctly, and whether fixing the six montages' "End" sections resolves the remaining 5-second pauses between activities.

## Known simplifications / deliberate scope decisions (carry these forward, don't "fix" without asking)

- Only `DT_Drugs`/`DT_Presets`/`DT_DatingProfiles` are real `UDataTable` assets; hormone/brain-region/neurotransmitter/emotion/MH/thought-template/development-phase/memory-category/therapy/stimulus tables are still hardcoded C++ (editor-access gap for those specific tables hasn't been closed, not a design preference) — same migration pattern available, just not applied yet.
- Character creation UI defaults every new character to the "healthy" preset; no multi-step creation wizard (name/sex/backstory) yet — user re-applies a different preset via the existing preset buttons after creating. Note: `UBioMindCharacterSubsystem` was observed (headless log) to already have a default active character (named "Default") before any explicit creation call — the Dating flow's "create if none exists" branch is a safety net for a genuinely empty subsystem, not the common path.
